# Database Normalization Checker
 
Connects to **one** MySQL, PostgreSQL or Oracle database, lists its tables, lets
you tick the tables to check, determines the exact normal form of each ticked
table (up to BCNF), and reports every table that is **below 3NF** as a
graph-like card: the table in full, the functional dependencies found with
confidence scores and real-value evidence, the reason it fails, and a
one-sentence recommendation.
 
Built for pre-deployment vetting inside an offline private network. It follows
the same conventions as the Link & Navigation Audit Tool (FastAPI backend that
also serves a plain HTML/CSS/JS frontend, SQLite for the last result, system
fonts only, no CDN).
 
> Status: design phase. See `docs/BUILD_PLAN.md` and `docs/BUILD_ORDER.md`.
 
---
 
## Where it runs
 
| Piece | Details |
|---|---|
| Tool VM (vm1) | Windows 64-bit, Python 3.12.10, no internet |
| Targets | Other VMs (Windows or Linux), each hosting an application and its database |
| Connection | vm1 connects over the network to the DB port (default or custom) with a DB URL, port, username and password entered per run |
| Databases | MySQL, PostgreSQL, Oracle (any currently supported, non-EOL version) |
| Scope per run | One database (Oracle: one schema); you choose which of its tables to scan |
 
The tool is **black-box at the OS level**: it never logs into the target VM,
only talks to the database port.

## What you get
 
1. **Form and Connect**: DB type, host, port, username, password and SSL
   option (certificate verification is skipped, as on the rest of the
   vetting network). **Connect** lists the databases (system and template
   databases excluded); you tick one and list its tables. No rows are read.
2. **Table picker**: every table with a checkbox (all ticked by default), column
   count, primary key yes/no and foreign key count; Select all, Select none, a
   filter box, and a counter ("12 of 42 selected"). Only ticked tables are scanned.
3. **Live scan view**:
   - one status row per ticked table: queued, **checking** (with the current
     step), or its verdict as soon as it is done;
   - a card appears the moment its table finishes;
   - a time line: `Checking 12 of 42 · elapsed 0:45 · about 2 min remaining ·
     estimated total 2 min 45 s (rough)`; "rough" disappears once the estimate is
     based on measured speed;
   - a Stop button that keeps the partial results.
4. **Headline**: one line, for example
   `12 of 42 tables scanned (30 not selected): 3 faulted, 1 suspected, 1 insufficient data, 7 clean`.
5. **Faulted-table cards** (graph-like, drawn as SVG):
   - the whole table with every column, primary and foreign keys marked
   - arrows from each determinant to the columns that depend on it
   - the exact normal form reached (1NF, 2NF, ...)
   - evidence per functional dependency, for example
     `Confidence Score: 96 (chance of coincidence about 1 in 10^48)`, counts,
     exceptions, cross-table support and real example values
   - why it fails 3NF, in one or two sentences
   - a one-sentence recommendation
6. **Suspected cards** (dimmed): same layout, lower-confidence findings.
7. **Last scan panel**: only the most recent result is kept.
8. **PDF export**: generated by the backend on request, never stored.
Phase 2 (built last): **EOL check** of the DB version and **possibly unused
table** detection.

## How it decides (summary)
 
Full detail is in `docs/DESIGN.md`.
 
- Data can disprove a functional dependency (FD) but never prove one, so every
  FD is scored by how unlikely it is that the data looks this way **by pure
  chance**, not trusted just because it holds in the data.
- Declared primary, unique and foreign keys are treated as certain.
- FDs are found exactly from the rows (TANE-style search, determinants of 2
  columns, 3 on tables from 1 000 rows, and every part of a declared composite
  key). Meaningless ones are removed.
- The chance of coincidence is calculated in closed form and corrected for the
  number of candidates tested (many guesses mean some look real by luck). A
  candidate also needs real repetition in the data (at least 5 repeated rows).
- Dirty data: up to 3% exception rows are allowed, but only inside groups of 3 or
  more rows with a clear majority value.
- Cross-table evidence: if a table repeats a column of the table it references
  through a declared foreign key, with matching values, that is near-certain
  redundancy.
- Normal forms are decided from candidate keys plus the strong FDs.
- A table is flagged only when it is **below 3NF**. 3NF but not BCNF is not
  flagged (its exact form is still recorded).
**What the score means:** the Confidence Score says how unlikely the data would
look like this if no dependency existed. It is **not** the probability that the
dependency is a real business rule.

## Safety and privacy
 
- **Read-only**: only `SELECT` and metadata queries, inside read-only
  transactions. The tool never writes to a target even if the account allows it.
- **Credentials are never saved.** The Connect step closes its connection after
  listing tables; the scan step uses the credentials still in the browser form.
  They live in memory only for the duration of a scan.
- **Only the last scan result is stored** (SQLite, overwritten each run). It
  contains the findings and the evidence example values shown on the cards; it
  contains no credentials and no full table dumps.
- The web server binds to `127.0.0.1` only. Passwords are never written to logs.
---
 
## Logs and error messages
 
Nothing fails silently.
 
- **Log file:** `backend/logs/dbnorm.log` (rotating, 5 files of 5 MB) plus the
  console. Every step is logged: connect, read-only setup, version, table list,
  schema read, then per table count, load, dependency search, scoring and verdict,
  and finally save and export. Logs contain names, counts and error codes, never
  passwords or row values.
- **In the UI:** a failure shows a plain message, a hint, the failed step, an
  error code and the scan id. For example: *"Database connection not
  established: host unreachable or port closed."*
- **Find the cause:** search the log for the scan id or error code shown in the UI.
- A table that cannot be read is listed as not analysed; it is never reported as clean.
Error codes and their meanings are in `docs/DESIGN.md` (section 13).

## Requirements
 
- Python 3.12 (3.12.10 on vm1)
- Windows 64-bit for the offline build (wheels target `win_amd64`, `cp312`)
- Network access from vm1 to the target DB port
Dependencies (bundled as wheels, see `docs/OFFLINE_PACKAGING.md`):
FastAPI, uvicorn, SQLAlchemy, PyMySQL, `cryptography`, pg8000, python-oracledb
(thin mode, no Oracle client needed), reportlab. `numpy` is **not** included
unless the benchmark in build step 8 shows it is needed.

## Setup
 
### Development machine (has internet)
 
```powershell
cd db-norm-tool
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt -r requirements-dev.txt
uvicorn app.main:app --reload --port 8770 --app-dir backend
```
 
Open `http://127.0.0.1:8770/`.
 
### Offline install on vm1
 
```powershell
python -m venv venv
venv\Scripts\activate
pip install --no-index --find-links wheels -r requirements.txt
cd backend
uvicorn app.main:app --port 8770
```
 
Building the wheels folder and the ISO is covered in `docs/OFFLINE_PACKAGING.md`.

## Using it
 
1. Pick the DB type, fill in the connection fields and click **Connect**. Tick one database and list its tables.
2. Tick the tables to check (all are ticked by default) and click **Scan selected tables**.
3. Watch the status list and the time line. Each table shows "checking" and then
   its verdict; cards appear as tables finish. **Stop scan** keeps partial results.
4. Read the headline, then the cards. Dimmed cards are suspected, not confirmed.
5. **Export PDF** to take the result with you. Re-open the previous result from
   the Last scan panel.
Connection fields:
 
| DB type | Required fields | Notes |
|---|---|---|
| MySQL | host, port (3306), user, password, database | MySQL 8 default auth needs `cryptography` (bundled) |
| PostgreSQL | host, port (5432), user, password, database | schema defaults to `public`, override if needed |
| Oracle | host, port (1521), user, password, service name, schema | thin mode; a "database" is a schema |

## Tuning (`backend/app/config.py`)
 
| Setting | Default | Meaning |
|---|---|---|
| `SERVER_PORT` | 8770 | Keep launcher scripts in sync |
| `MAX_LHS_SIZE` | 2 | Max columns in a determinant (free search) |
| `MAX_LHS_SIZE_LARGE` | 3 | Same, for tables with at least `LARGE_TABLE_ROWS` rows |
| `LARGE_TABLE_ROWS` | 1000 | Row count from which size-3 determinants are searched |
| `MAX_ROWS_PER_TABLE` | 50000 | Larger tables are analysed on the first N rows by key order and marked sampled |
| `MIN_ROWS_FOR_DATA_FDS` | 10 | Below this, data-derived FDs are not trusted |
| `MIN_REPEATED_ROWS` | 5 | Materiality gate: rows that carry duplicated information |
| `STRONG_CONFIDENCE` | 75 | At or above: confirmed finding |
| `STRONG_CONFIDENCE_CROSS_TABLE` | 60 | Lower bar when another table supports the finding |
| `SUSPECT_CONFIDENCE` | 50 | At or above (and below strong): dimmed "suspected" |
| `NEAR_FD_MAX_ERROR` | 0.03 | Max fraction of exception rows for a near-FD |
| `NEAR_FD_MIN_GROUP` | 3 | Smallest group in which a disagreement counts as dirty data |
| `NEAR_FD_SCORE_CAP` | 90 | Highest score a near-FD can get |
| `SAMPLED_SCORE_CAP` | 85 | Highest score on a sampled table |
| `CROSS_TABLE_MATCH_MIN` | 0.97 | Match rate for cross-table support |
| `ETA_DEFAULT_SECONDS_PER_UNIT` | set in step 8 | Starting speed for the time estimate |
| `ETA_PRIOR_UNITS` | set in step 8 | How much weight the starting speed has |
| `ETA_TICK_SECONDS` | 5 | How often the estimate is refreshed |
| `SSE_HEARTBEAT_SECONDS` / `STREAM_TIMEOUT_SECONDS` | 15 / 45 | Live stream keep-alive and loss detection |
| `QUERY_TIMEOUT_SECONDS` | 30 | Per query |
| `LOG_LEVEL` | INFO | Use DEBUG only when diagnosing (still never logs secrets or values) |
| `LOG_FILE` | `backend/logs/dbnorm.log` | Rotating log file |
| `LOG_MAX_BYTES` / `LOG_BACKUP_COUNT` | 5 MB / 5 | Rotation size and number of old files |
 
All defaults are starting values; they are tuned against the test databases
(`docs/TEST_PLAN.md`).

## Known limits
 
- The report is guidance, not proof. On tables of about 100 rows some true
  violations cannot be proven from the data; they show as suspected or not at all.
- The tool cannot know business meaning: a rule that should hold but does not
  appear in the data will not be found.
- A 3-column determinant that is not part of a declared key is searched only on
  tables from 1 000 rows. Smaller tables are not searched for it.
- Cross-table evidence uses declared foreign keys only.
- 1NF checks are heuristic (delimited values, repeating columns, missing key).
- The time estimate is approximate; it is marked "rough" until it is based on
  measured speed, and a slow network or a locked table can make it drift.
- Oracle is tested on a recent free edition only; older supported versions are
  unverified until tried.
- The EOL table (phase 2) is bundled and must be updated by hand; the report
  shows its "as of" date.
- "Possibly unused" tables (phase 2) are a heuristic guess, not a fact.

## Troubleshooting
 
| Symptom | Cause / fix |
|---|---|
| UI shows an error code and scan id | Search `backend/logs/dbnorm.log` for that scan id; the log line has the technical cause. Codes are listed in `docs/DESIGN.md` section 13 |
| "Database connection not established" | The message names the reason (unreachable, timed out, credentials rejected, database not found, SSL). Cannot connect: check the port with `Test-NetConnection <ip> -Port <port>`; target DB must allow remote connections from vm1 (MySQL `bind-address`, PostgreSQL `listen_addresses` and `pg_hba.conf`) |
| MySQL auth error (`caching_sha2_password`) | `cryptography` wheel missing from the install |
| Oracle `DPY-6001`/service not found | Use the service name (for example `FREEPDB1`), not the SID, and the correct port |
| Many tables show "insufficient data" | Tables have too few rows; data-derived FDs are not trusted below `MIN_ROWS_FOR_DATA_FDS` |
| "Live progress connection was lost" banner | The browser lost the stream; the scan keeps running and the page re-syncs. If the backend was restarted, start the scan again |
| Time estimate keeps changing | Normal early on ("rough"); it settles as tables finish. Very large or locked tables can still make it drift |
| A table shows "error" with a code | That table could not be read (permission, timeout, dropped); the rest of the scan is unaffected. The code is in the log |
| Stale UI after update | Hard refresh; restart the backend for backend changes |
| Wheel install fails offline | A dependency is missing from `wheels/`; rebuild with the command in `docs/OFFLINE_PACKAGING.md` and re-test with `--no-index` |
